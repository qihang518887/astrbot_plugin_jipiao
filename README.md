# 机票低价监控（AstrBot 插件）

v0.7.3 使用携程国内机票 H5 查价，沿用 `ticket-monitoring` 的持久化 Chromium 会话、手机模式、首页预加载与 `flightListSearchForH5` 响应解析流程。支持原有指令、LLM Tools、SQLite 任务、37% 观察策略、航司黑名单和 QQ 低价提醒；同时接受经停与中转且无航司筛选的模糊日期查询可选日历最低价后单日核实，观察期结束会 @ 用户汇总低价，决策期低于第二低价即可提醒。Python 3.12+。

## 升级与已有监控

代码目录与运行数据目录分开。标准 AstrBot 部署中：

| 目录 | 升级操作 |
| --- | --- |
| `data/plugins/astrbot_plugin_jipiao/` | 替换为新插件代码 |
| `data/plugin_data/astrbot_plugin_jipiao/` | 原样保留整个目录 |
| `data/plugin_data/astrbot_plugin_jipiao/flights.sqlite3` | 原样保留，不删除、不重新创建 |

上面的 `data/` 是 AstrBot 的数据根目录；自定义数据根目录或 Docker 挂载时，以实际部署路径为准。插件使用 `StarTools.get_data_dir("astrbot_plugin_jipiao")` 获取数据目录。

1. 暂停插件或停止 AstrBot，备份整个插件数据目录。SQLite 在停止后备份，避免只复制主文件而遗漏 WAL 中的记录。
2. 把旧配置中的 `data_source` 明确改为 `ctrip`，删除已不用的 `tuniu_cookies` 配置项。两项携程路径可以留空；已有自定义会话路径可以继续使用。
3. 更新插件代码并安装下面的依赖。手动覆盖文件时删除旧代码目录中的 `tuniu.py`、`tuniu_cookies.py`、`tuniu_login.py`，或直接用新包替换整个代码目录。数据目录保持原位。不要使用会清理插件数据的卸载操作。
4. 启动 AstrBot，管理员私聊发送 `/携程登录`，使用携程 App 扫码并确认。看到“携程登录成功”后再查询机票验证。
5. 发送 `/我的监控` 检查原条件、目标价和观察记录。已有监控无需重新设置；重新设置反而会重置观察。

`data_source` 只接受 `ctrip` 和 `mock`。旧 `fli`、`tuniu` 值会直接报配置错误，不会自动映射。插件已移除途牛查询、Cookie、登录命令及其测试；运行时没有旧数据源适配分支。内置 `fli.models` 仅用于机场/航司名称校验，不参与 Google 查价。

数据库结构和业务算法未因这次登录改造而改变。任务条件、经停/中转开关、创建时间、观察记录、上次提醒价、通知会话与 revision 全部保留。旧观察基准继续使用，不同来源的报价口径和覆盖可能不同。`mock` 仍使用独立的 `mock.sqlite3`。

## 在机器人会话中登录携程

先在 **AstrBot 实际运行的 Python 环境** 安装依赖和 Chromium：

```bash
python -m pip install -r /实际插件路径/astrbot_plugin_jipiao/requirements.txt
python -m playwright install --with-deps chromium
```

Docker 部署在 AstrBot 容器或镜像内执行，并持久化插件数据目录。服务器无须图形桌面；登录与查询都使用无头 Chromium。Linux ARM64 需具备 Playwright Chromium 的系统依赖，当前尚未在用户的 ARM64 实机验证。

管理员私聊机器人发送：

```text
/携程登录
```

插件在服务器打开携程官方登录页，点击“扫码登录”，截取官网实际生成的二维码发回当前私聊。使用手机携程 App 扫描图片并确认。插件最多等待 120 秒，以官方页面跳转回登录指定的首页作为登录完成信号，再保存 Cookie 和 localStorage。二维码失效或等待超时后重新发送命令。

登录浏览器使用独立的临时目录，关闭后清理。只有确认成功才原子替换会话文件；超时、取消或浏览器错误不改原会话，卸载插件会结束尚在等待的登录。登录异常直接报错，不增加轮换身份、自动重试或其他登录路径。共享携程账户沿用原登录命令的管理员、私聊权限。

默认保存至插件数据目录 `cookies/ctrip_state.json`，后台查询自动使用，不需要在其他电脑登录或复制会话。设置了 `ctrip_storage_state` 时，登录保存和查询读取使用同一个自定义路径。会话凭证独立于 `flights.sqlite3`，登录不会重建监控。

v0.6.1 不导出或恢复 IndexedDB 查询缓存，避免 Playwright 恢复该缓存时出现 `IDBObjectStore` 键错误。已有会话文件即使包含 IndexedDB，读取时也仅取 Cookie 和 localStorage；成功查询后写回相同格式。升级不要求删除会话或浏览器目录。所有查询使用明确指定的会话路径，缺少会话文件直接要求 `/携程登录`，不转用浏览器缓存或另一个本地文件。

“登录成功”表示官网完成登录，不保证机票接口在服务器 IP 上一定可用，应再查一次机票。会话失效时再次发送 `/携程登录`。会话文件含登录凭证，不要提交 GitHub 或发送到聊天。Linux 新文件权限为 600，文件及目录应允许 AstrBot 用户读写。

`ctrip_session` 仅保留为可选的本地调试导出工具，机器人登录不依赖它。安装包不含 `.local`、浏览器资料、登录会话或数据库。

## 单次查价

当前工作区运行以下命令，不创建监控、不访问监控数据库、不发送 QQ 消息：

```powershell
rtk proxy astrbot_plugin_jipiao/.venv/Scripts/python.exe -m astrbot_plugin_jipiao.smoke --dep 大连 --arr 上海 --date 2026-11-05 --storage-state astrbot_plugin_jipiao/.local/ctrip_state.json
```

`--profile-dir` 指定浏览器资料目录，CLI 默认源码目录 `.local/ctrip_browser`；`--storage-state` 默认源码目录 `.local/ctrip_state.json`。CLI 默认路径与 AstrBot 运行时的数据目录不同，服务器测试应显式指定与插件配置一致的两个路径。

在服务器插件包的父目录中测试（路径、日期换成实际值）：

```bash
python -m astrbot_plugin_jipiao.smoke --dep 大连 --arr 上海 --date 2026-11-05 --storage-state /实际数据目录/cookies/ctrip_state.json --profile-dir /实际数据目录/browser/ctrip
```

`--allow-stopovers`、`--allow-connections` 分别允许经停和中转；`--allow-stops` 同时允许。`--time-window 08:00-18:00`、`--airlines CA,MU` 验证原筛选条件；`--mock` 是明确的模拟查询。

## 指令、LLM Tools 与范围

- `/携程登录`：管理员私聊扫码，直接保存服务器会话。
- `/机票监控 出发地 到达地 YYYY-MM-DD [时间段] [航司] [目标价] [直飞|接受经停|接受中转|接受经停与中转]`
- `/我的监控`：条件、观察阶段、记录的低价、上次提醒价与最近状态。
- `/取消监控`：停止当前平台账号的任务。
- `search_flights`：自然语言查价。默认先直飞，无匹配报价再依次查经停、中转备选。
- `set_flight_monitor`、`get_flight_monitor`、`cancel_flight_monitor`：自然语言设置、查看、取消监控。

```text
/机票监控 大连 上海 2026-11-05 - - 350
/机票监控 大连 上海 2026-11-05 08:00-18:00 国航,东航 500 接受经停
/机票监控 大连 上海 2026-11-05 - - 500 接受中转
```

一个平台账号一个任务，重新设置会覆盖并重置观察。通知发送到最后一次设置所在的会话。仅单程、1 成人、经济舱、人民币。中文城市“上海”包括 SHA/PVG；明确填写机场码 SHA 则只匹配虹桥，不能把浦东报价算进去。时间段约束首段起飞，航司白名单要求全部航段营销航司符合；航司黑名单命中任一航段即排除整程。

## 航司黑名单

在原有“航司”参数里，给每家要排除的航司加 `!`，例如 `!春秋,!联航` 或 `!9C,!KN`。只有黑名单时，其余航司不限，无需列出所有愿意乘坐的航司。支持中文名称、别名、大小写二字码、中文逗号与全角 `！`，保存时规范为 `!9C,!KN` 并去重。每个排除项都需要自己的 `!`。

```text
/机票监控 北京 上海 2026-12-01 - !春秋,!联航
/机票监控 北京 上海 2026-12-01 - !9C,!KN 500
```

自然语言可说“监控12月1日北京到上海，不要春秋和联航，其余航司都可以”；`search_flights`、`set_flight_monitor` 的 `airlines` 参数同样填写 `!9C,!KN`。确认回复、`/我的监控` 与状态工具会显示“排除 9C、KN；其余航司不限”。这项筛选针对营销航司，不推断接口未提供的实际承运航司。

查询结果列表、直飞无结果后的经停/中转备选、定时监控均使用同一筛选逻辑，先排除再选最低价。任一航段营销航司命中黑名单，就排除整条行程，被排除的价格不进入观察记录或价格推送；仅黑名单不会误变成“只看这些航司”。旧 `CA,MU` 白名单继续可用；若混合填写，例如 `CA,MU,!MU`，黑名单优先，最终仅允许 CA。

黑名单也是航司条件，因此有黑名单时不启用当前混合价格日历，保留原日期查明细。名单存入原有 `airlines` 字段，重启继续生效，升级无需迁移或重建任务；修改已有监控的筛选条件仍按原来的重设规则重新观察。

| 用户范围 | allow_stopovers | allow_connections |
| --- | --- | --- |
| 仅直飞 | false | false |
| 直飞、经停 | true | false |
| 直飞、中转 | false | true |
| 全部 | true | true |

航段内的 `fsitem` 是经停，多个 `mutilstn` 航段按完整航班号和换机场情况分类。同一行程有经停又有换乘，需要两个开关都开启。经停只返回城市与时长时不编造中间到离时刻；只在中转时间能确认时标注过夜。同航班号不保证不换机。备选查询不修改任务，后台没有结果时不会扩大已保存的范围。

## 模糊日期低价日历

日历默认关闭，不向 LLM 暴露一个可随意打开的布尔参数。插件检查当前原始用户消息：只有中心日期附近明确出现“左右、前后、附近、大概、大约、差不多”等日期模糊词、没有航司白名单或黑名单，且用户明确同时接受经停与中转（`allow_stopovers=true`、`allow_connections=true`），才走日历。单独说“大概多少钱”不表示日期可变，不会启用。模拟模式也不访问真实日历。

**v0.7.2 航程限制优先于日历。** 当前接入的日历返回每日聚合参考价，没有可用于分别筛除经停、中转的行程分类；旧版只在候选日明细阶段应用开关，可能先被禁止的行程低价选错日期。修复后，只要关闭任意一项，就在发请求前跳过日历，保留用户给出的中心日期，仅查当天符合原开关的明细，并明确解释跳过原因。默认仅直飞因此不会使用这种混合价格日历；仅接受经停、仅接受中转也同样跳过。即使当天没有结果，也不追加其他日期或扩大航程范围。LLM 不得为了启用日历擅自把开关设为 true。

| 用户表达 | 行为 |
| --- | --- |
| “查11月5日大连到上海” | 明确日期，只查11月5日 |
| “查11月5日的票，大概多少钱” | 模糊的是价格，只查11月5日 |
| “查11月5日左右大连到上海” | 默认仅直飞，跳过混合价格日历，只查11月5日的直飞明细 |
| “查11月5日左右大连到上海，接受经停和中转” | 查11月2日至8日的日历参考价，核实最低价候选日 |
| “查11月5日左右大连到上海，接受经停但不接受中转” | 跳过混合价格日历，只查11月5日的直飞及经停明细 |
| “查11月5日左右大连到上海，接受中转但不接受经停” | 跳过混合价格日历，只查11月5日的直飞及不含经停的中转明细 |
| “大概11月5日出发，只要国航” | 指定航司，关闭日历，按原日期和航司查询 |
| “11月1日前后” | 窗口截断为11月1日至4日，不跨到10月 |

中心日由 LLM 解析为 `YYYY-MM-DD`，是否启用仍根据原话判断。窗口为中心日前后各三天，包含中心日共最多七天，只取当月且不早于北京时间今天。原话给出的完整月份/日期与工具传入的中心日不符，或含“必须、只能、仅限、不改日期”等约束时，不启用日历。缺少具体中心日时不自动猜测范围。

符合日历启用条件时，只发一次日历请求。接口可能返回超过窗口的日期，但插件只保留上述同月窗口，不再追加跨月或逐日请求。选择最低参考价日期；同价优先离中心日最近的日期，再同距选较早一天。只详细查询这个候选日一次，继续应用机场和时间段等用户条件，经停/中转开关与日历请求保持一致；日历核实没有普通查询的经停/中转递进备选，也不因价格失效自动扫描其他六天。

结果同时显示最低参考价、选中日期和单日明细价格。相等则报告查到同价；明细更高、无匹配行程或接口失败时，明确标记日历价未核实/未成立，不当成真实低价。若明细更低则使用明细价。这里的最低日期只是日历候选，不代表已经逐日核对整周明细。日历价不保证税费、会员或机场等全部口径一致。

日历发现仅用于即时 `search_flights` 查询，不自动创建监控、不改变已有任务日期，也不写入 `lowest_3_json` 或 `last_pushed_price`。定时监控保存了明确日期，仍只查任务原日期，只有原价格策略决定是否记录/推送。

## 提醒、算法与存储

数据仍放在 AstrBot 插件数据目录：真实 `flights.sqlite3`、模拟 `mock.sqlite3`。`tasks` 表每用户一行，保存查询条件、观察期最低三个不同价格、最近报价、上次提醒价、观察结束通知时间、通知会话和 revision；不保存每轮全部历史。取消或北京时间出发日零点到期时删除任务。重启保留观察记录与提醒状态。

后台任务串行查询，默认任务之间等待 45 秒并有正负 3 秒抖动，即 42—48 秒；每轮结束后等待 3600 秒（一小时）。实际同一用户的周期还包含全轮查询和任务间隔耗时。旧配置即使仍保存 30 秒、1800 秒，升级后也会分别按至少 45 秒、3600 秒运行；可配置更长间隔。新任务可唤醒空闲轮询，但刚检查过的旧任务不会因此提前重复查询。这两项控制后台任务，不是对所有即时聊天请求新增全局限流。没有按临近起飞自动加快、固定推送时刻或夜间免打扰。

设置目标价时，首次不高于目标价即提醒，之后只有进一步降价才提醒。未设置目标价时使用 37% 策略：起飞前 60 天以外等待；从 `max(创建时间, 起飞前60天)` 到起飞前七天的剩余时间中，前 37% 观察、至少 12 小时；对每次查询得到的符合条件最低价，按金额去重，保留观察期出现过的最低三个不同价格，同一价格间隔多久再次出现都不重复占位，并保留第一次记录时间。

决策期使用观察期的**第二低价**，当前匹配报价必须**严格低于**它才提醒，等于不提醒。例如记录 `400、450、500` 元，则 `449` 元可提醒、`450` 元不提醒；即使曾提醒 `400` 元，之后变成 `420` 元仍可提醒。与上次成功提交推送相同的价格不重复提醒；其他符合阈值的价格提醒后，该价格再次出现可以重新提醒。只有两种价格时取第二种；只有一种时取唯一记录，仍要求严格低于；没有观察记录则等待临期兜底。决策期不会改写已完成的观察基准。进入起飞前七天优先兜底，首次按匹配报价提醒，后续仅进一步降价再次提醒。经验规则不保证最低买入价。

观察期结束后，后台下次处理该任务时向设置任务的原会话发一条汇总：群聊使用真实 `At` 组件 @ 原用户，私聊直接发文字，并列出从低到高的三种金额；不足三种的位置显示“暂无记录”。此汇总独立于查价成功与否，也不受最近查价间隔阻挡，不会消耗低价提醒机会。它随后台轮询检查，**不是精确到秒的定时通知**；发送失败保留重试机会，适配器成功接收后写入 `observation_notified_at`，重启后不重复发送已记录成功的汇总（适配器接收不等于用户已读）。到起飞前七天而提前结束的观察期也会汇总；直接在兜底期创建、设有目标价或已经到期的任务没有观察结束汇总。取消/覆盖任务后不发送旧任务的延迟结果。

v0.7.1 自动增补观察结束通知字段，保留现有条件、创建时间、低价记录和上次推送价，无需重新创建任务。升级前已结束观察、仍未到期的无目标价任务，会在下次处理时补发一次汇总；重新设置任务会清空观察和汇总发送状态。

v0.6.2 打开数据库时会自动合并旧版的重复金额，不重置任务、观察起点或已推送价格。例如 `400、400、500` 会变成 `400、500`。旧版被重复记录挤掉而未保存的其他价格无法恢复；仍在观察期的任务会继续用后续查询补充，决策期则使用保留的去重记录。

查询失败不会消耗提醒机会，发送失败保留下一轮重试机会，状态见 `/我的监控`。QQ 官方群适配器重启后可能需要在原群发送 `/我的监控` 恢复群场景，并开启群主动发言权限。平台接受消息不等于已读，不保证恰好送达一次。
